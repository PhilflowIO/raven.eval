# Environment of the vLLM leg: the engine (`vllm serve`, started by launch.py),
# the transformers stand-in (transformers_server.py) and the shim in front of both
# (shim.py). One environment, so the shim reports the engine it was installed
# with, and one engine for every vLLM model: a model never gets an engine of its
# own, so all vLLM rows of a round answer to the same version.
#
# The engine follows the newest vLLM release; the pin exists so a run can name
# and reproduce what served it, not to hold a model on an old engine. Bumping it
# moves every vLLM row, so a bump is followed by re-measuring all of them.
#
# Every version that decides output is exact: an unpinned "vllm[audio]>=0.25"
# once moved a host to 0.28 without anyone asking, and 0.28's FlashInfer
# top-k/top-p sampler JIT-compiles its kernel at warm-up — on a host without a
# CUDA toolkit every model then died before serving. FlashInfer's kernels come
# prebuilt in two packages, and vLLM needs both:
#   - flashinfer-cubin is what vLLM checks for. Without it (and without nvcc and
#     ninja) vLLM 0.33 switches FlashInfer off entirely and says so at start
#     ("FlashInfer kernels are disabled", has_flashinfer in
#     vllm/utils/flashinfer.py); it never looks at the jit-cache. It is
#     CUDA-independent and published only on FlashInfer's own index (/whl).
#   - flashinfer-jit-cache holds the JIT modules (sampling and the like) built for
#     exactly this flashinfer + CUDA 13.0 pair (/whl/cu130). Since 0.7 it is a shim
#     that pulls one provider wheel per GPU architecture; an RTX 30xx (sm86) runs
#     the sm80 provider's kernels.
# Bump vllm, flashinfer-python, flashinfer-cubin and flashinfer-jit-cache together:
# vllm pins flashinfer-python itself, flashinfer refuses kernels of another
# version, and vLLM warns when cubin or jit-cache drift from flashinfer-python.
#
# torch (2.14.0, CUDA 13.0 wheels: needs an NVIDIA driver >= 580) is pinned by
# vllm itself. transformers is pinned here: vllm only bounds it, and it decides
# the stand-in's output and the HF processors several vLLM models run through.
#
#   uv venv --python 3.12 <venv>
#   uv pip install --python <venv>/bin/python -r serving/vllm/requirements.txt
#
# soundfile comes with vllm[audio]; fastapi, uvicorn and httpx come with vllm
# too, but the shim imports them directly, so they are named here.
#
# NeMo Speech is installed here as a vLLM plugin, not as a second engine: its
# entry point `nemo_speechlm` (vllm.general_plugins) registers the SpeechLM
# architectures (Nemotron3_5TranscribeForConditionalGeneration) with this same
# vLLM. A recipe loads it only when it names it (`vllm_plugins`); launch.py sets
# VLLM_PLUGINS for every vLLM recipe, so all other models start with no plugin.
# Pinned to a fork commit, not a release: NeMo pins its `vllm` extra to 0.32.0,
# and on 0.33.0 the plugin aborted `vllm serve` because vLLM moved the chat
# parser it adapts (runtime_compat.py vs vllm/renderers/chat_utils/
# chat_message.py), and vLLM's Marlin padding of a misaligned MoE intermediate
# size reshapes w13 as two shards, which aborts loading of NemotronH's gate-less
# experts at tensor-parallel 2 (N = 928 per card). The fork commit is NeMo main
# e5d79d5a plus those two fixes, the first proposed upstream as
# https://github.com/NVIDIA-NeMo/Speech/pull/16505; move back to an
# NVIDIA-NeMo/Speech commit or release once both are merged (#78). The
# `vllm` extra is NOT installed (it would pull vllm 0.32.0); peft is the rest of
# it. Resolved with the lines above (uv pip compile, Python 3.12, x86_64 Linux,
# 2026-11-02): vllm, torch, transformers, flashinfer, librosa and numpy stay
# exactly as without NeMo; only fsspec (2025.12.0) and packaging (24.2) resolve
# lower.
#
# raven-vllm-plugin (serving/vllm/plugin in this repository) keeps vLLM 0.33.0's
# Transformers backend from killing its engine on a batch of audio clips of
# different lengths: _select_item_kwargs (multimodal.py:1154-1165) hands the model
# a per-clip tensor as a one-element list (raven.eval#93). Unfixed upstream as of
# 2026-11-08. Pinned to the commit that added it: a change to the plugin moves this
# line, and with it the venv stamp that rebuilds the environment. VibeVoice-ASR
# loads it through `vllm_plugins`; remove it once a pinned vLLM carries a fix.
